# P6.5 线性自动工作流维护说明

## 1. 当前能力

用户可以在“自动流程”页面选择并保存以下步骤：

```text
榜单采集 -> 内容分析 -> 歌词创作 -> 歌词审核 -> 音乐创作
```

步骤可以减少，但必须保持数据依赖顺序。自动作词必须包含内容分析；歌词审核必须
包含作词；音乐创作必须包含作词，并接收审核通过或人工确认后的最新歌词版本。
歌词审核是可选步骤，模板需要指定当前用户可使用的审核智能体、及格分和补充要求。
首期最大审核轮数固定为 3，及格分默认 80。

## 2. 数据传递

工作流执行器统一负责传参，Agent Service 之间不直接互相调用：

```text
CollectionTask.snapshot_id
-> 查询该快照前 30 首 RankingEntry.id
-> AnalysisCreateRequest.entry_ids

AnalysisReport.id
-> LyricsCreateRequest.analysis_report_id
-> 读取 direction_index 对应创作方向

LyricsVersion.id
-> ReviewRun + Lyrics Assistant 自动修改
-> 审核通过或人工确认后的 LyricsVersion.id
-> MusicCreateRequest
-> Suno MusicProvider 参数
-> MusicResult.id
```

审核步骤每轮把当前歌词版本交给所选审核智能体。低于及格分时，执行器读取审核总结
和修改建议，调用现有歌词 AI 助手生成预览并确认成一个新 `LyricsVersion`，然后继续
审核。达到及格分后，最新歌词版本成为审核步骤的 `output_id`，音乐步骤只能消费这个
编号。平台内五步传参已经完成；未配置可用音乐 Provider 时，音乐步骤会明确失败并
停止流程，不产生模拟结果。

因此“步骤完成”必须同时得到可用的 `output_id`。上游失败或缺少产出时，流程立即失败并保留下游等待状态。

## 3. 数据表

```text
workflow_templates   保存名称、所选步骤和参数
workflow_runs       保存一次运行的配置快照和总状态
workflow_run_steps  保存每一步的 task_id、output_id、状态、错误和 result_detail
```

审核步骤的 `result_detail` 保存审核周期、每轮分数、审核记录编号、歌词版本编号、
修改后版本和人工决定。模板被修改后不会改变已经创建的运行；运行保存的是启动时
配置快照。

## 4. 请求路线

```text
WorkflowsPage
-> frontend/src/api/workflows.ts
-> routes/workflows.py
-> services/workflows.py
-> rankings / analysis / lyrics Service
-> PostgreSQL
```

启动和审核决定接口返回 HTTP 202，后台继续执行。前端检测到 `pending` 或 `running`
后每 2.5 秒刷新运行列表；`paused` 不会自动轮询执行，它表示流程正在等待用户判断。

## 5. 审核循环与人工决定

默认状态路线：

```text
歌词产出
-> 第 1 次审核
-> 未达标：按审核意见生成新歌词版本
-> 第 2 次审核
-> 未达标：再次生成新歌词版本
-> 第 3 次审核
-> 达标：继续下游
-> 仍未达标：流程进入 paused
```

暂停后用户有四种选择：

| 操作 | 行为 |
|---|---|
| 接受当前歌词并继续 | 把当前审核步骤标记完成，下游接收当前歌词版本 |
| 提交修改要求 | AI 助手按要求创建新版本，然后从新的三轮审核周期开始 |
| 已手工修改，重新审核 | 读取该作词任务的最新版本，然后从新的三轮审核周期开始 |
| 重新生成歌词 | 调用作词重新生成创建新版本，然后从新的三轮审核周期开始 |

人工决定会写入审核步骤详情。恢复时保留已经完成的上游步骤和历次审核周期，不重复
采集、分析或作词。流程暂停期间仍占用全局活动流程名额，不能启动第二条流程，也不能
删除当前运行记录。

## 6. 运行约束

- 全系统同一时间只启动一条自动流程。
- 分析到作词，以及作词、审核和自动修改之间的连续文本 AI 调用默认冷却 15 秒，
  使用 `WORKFLOW_STEP_DELAY_SECONDS` 调整；每两个调用之间只等待一次。
- 超过 `WORKFLOW_STALE_SECONDS` 的 `pending/running` 流程会被标记为
  `WORKFLOW_TASK_INTERRUPTED`；等待人工决定的 `paused` 流程不按运行超时处理。
- 当前后台任务运行在 FastAPI 进程内；服务重启会中断任务。正式部署并发增加后再迁移到 Redis 队列 Worker。
- 手工运行分析或作词仍是同步请求，不属于自动流程后台调度。

## 7. 常用接口

```text
GET    /api/v1/workflows/templates
POST   /api/v1/workflows/templates
PUT    /api/v1/workflows/templates/{id}
DELETE /api/v1/workflows/templates/{id}
POST   /api/v1/workflows/templates/{id}/runs
GET    /api/v1/workflows/runs
DELETE /api/v1/workflows/runs
GET    /api/v1/workflows/runs/{id}
DELETE /api/v1/workflows/runs/{id}
POST   /api/v1/workflows/runs/{id}/review-decision
```

`review-decision` 的 `action` 为 `accept`、`retry`、`revise` 或 `regenerate`；
`revise` 必须提供 `instruction`。运行历史支持单条和批量删除。删除 `workflow_runs`
时会级联删除对应步骤轨迹，但不会删除模板或各步骤已经生成的产出。`pending`、
`running` 和 `paused` 状态不可删除；批量请求中存在无效编号或活动流程时整批拒绝。

## 8. 测试重点

`backend/tests/test_workflows.py` 覆盖：

- 采集快照真实传给分析任务。
- 分析报告真实传给作词任务。
- 各步骤保存任务编号和产出编号。
- 上游缺数据时停在失败步骤。
- 作词不能脱离分析单独加入自动流程。
- 运行历史批量删除会去重编号，并保留流程模板和步骤产出。
- 排队或运行中的流程不能删除。
- 审核低于及格线时自动修改，并把新歌词版本继续送审。
- 第二轮达标后，音乐步骤收到修改后的歌词版本。
- 连续三轮未达标进入 `paused`，且暂停流程阻止新流程和删除。
- 接受、按要求修改、读取手工最新版本和重新生成都能恢复审核流程。

前端 `frontend/src/lib/workflows.test.ts` 覆盖包括审核步骤在内的依赖联动。
