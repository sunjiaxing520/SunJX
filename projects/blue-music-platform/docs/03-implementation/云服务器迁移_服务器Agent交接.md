## 4. 为什么不能直接清空任务表

代码事实：

- `backend/app/models/favorite.py`：`favorite_items`通过`item_type + target_id`引用作品，**不是正文快照，也没有针对目标的数据库外键**。仅查外键完整性发现不了空收藏。
- `backend/app/services/favorites.py`：收藏类型为`analysis`、`lyrics`、`music`，详情分别读取`AnalysisReport`、`LyricsVersion`、`MusicResult`，还读取父任务。
- `analysis_reports.task_id -> analysis_tasks.id`使用CASCADE。
- `lyrics_versions.task_id -> lyrics_tasks.id`使用CASCADE。
- `music_results.task_id -> music_tasks.id`依赖父任务；音乐删除服务还会删除文件与收藏条目。
- 试听盒子按MusicTask归组；音乐提交时歌词快照在`music_tasks.lyrics`，来源版本/任务用于“歌词记录”定位。

迁移时先构造“收藏保护集合”，递归保留所需作品、父任务和引用。至少包括：

| 收藏类型 | 必须保留 |
|---|---|
| 分析 | 收藏行、AnalysisReport、所需AnalysisTask与正文/方向/证据；再检查真实榜单引用是否需保留。 |
| 歌词 | 收藏行、LyricsVersion、所属LyricsTask；若要完整来源定位，再保留相应分析来源。 |
| 音乐 | 收藏行、MusicResult、所属MusicTask、实际音频对象、歌词快照、名称/备注/标记；为维持原歌词定位保留来源LyricsVersion及其LyricsTask。 |

ID尽量原样保留；如重编号，必须维护映射并更新所有引用。SET NULL不代表允许用户体验无损地删除来源。
一批两首中仅收藏一首时，不能把整个任务/目录删掉；可以按规则清理另一首，但必须保留父任务与收藏首的文件。星标`MusicTask.is_marked`、歌词`is_saved`与`FavoriteItem`不是同一概念，已确认前两者本身不提供保留保护。

## 6. 凭证与配置迁移

- 绝不把`.env`、SSH密码/私钥、供应商Key、Token、数据库备份写进交接文档、Git或日志。
- 加密凭证逻辑在`backend/app/core/credential_crypto.py`，由`AI_CONFIG_ENCRYPTION_KEY`派生；该配置未显式设置时会退回`SECRET_KEY`。**不能改生产SECRET_KEY后才发现旧凭证无法解密。**
- 安全渠道取得旧加密材料，在隔离环境验证解密；如换生产加密材料，受控重加密全部相关配置后验证，或让客户重新输入凭证。JWT签名密钥可独立换新，旧登录失效属预期。
- Kimi开发测试Key不可不加区分作为客户生产Key；上线前配置客户凭证并验收，之后由用户吊销开发Key。
- Suno配置与回调签名secret也有加密值，不能只复制数据库而丢失解密条件。
- 不照抄当前Compose的默认数据库口令、开发SECRET_KEY、`ENVIRONMENT=development`、源码挂载与`--reload`。

## 7. 50GB服务器部署要求

1. 先盘点真实可用空间、系统/镜像/Todo/数据库/日志/备份占用，以及收藏音频实际总大小。50GB是标称盘，不是音频配额。
2. 建独立生产部署配置，推荐独立目录例如`/srv/blue-music`（示例，不得覆盖同名现有数据）。前端构建为静态资源，由反向代理提供；API与两个worker独立运行。
3. PostgreSQL、音频目录、必要日志持久化。`MUSIC_STORAGE_BACKEND=local`时显式绑定持久存储目录，API和worker必须读写同一目录。参考对象键`<task_id>/<result_id>.mp3`，按DB实际`storage_key`核对，不能假设全部是MP3。
4. 音频不只在数据库里：本机默认`D:\SunJX\projects\blue-music-platform\backend\storage\music`，实际以运行配置为准。必须连同收藏音频复制、验证大小/校验和；已有S3对象按实际后端处理，不能只拷本地目录。
5. 封面当前可能是供应商远程`image_url`，不保证永久有效；迁移时记录是否有本地副本，需要归档则安全下载并做对象清单，不能伪称已备份封面。
6. 设置磁盘阈值告警、日志轮转和备份保留；收藏不自动删除，因此容量可持续增长。接近阈值应提示扩容/迁对象存储，不得擅自删除收藏或记忆。不要把多份全量备份长期堆在同一50GB盘。
7. 保留与发布镜像分离的异机备份；不得使用`docker system prune --volumes`或`docker compose down -v`处理空间。

## 8. 三天清理功能是新增开发，不是已有能力

当前只明确已有“暂停流程超过48小时删除运行记录、保留产出”的逻辑（`backend/app/services/task_queue.py`），它**不是**未收藏作品72小时保留策略。不要把`RANKING_RETENTION_DAYS`改成3当作音乐清理已完成。

实现建议（先确认第2节）：

- 可配置、默认关闭的清理器，先支持dry-run；输出拟删除ID、字节数、保留原因，不输出正文或敏感配置。
- 若采用72小时，到期按作品生成时间计算，而非调度程序上次运行时间；时间戳统一UTC，界面可显示北京时间。
- 未完成、已提交供应商、等待回调、暂停待人工处理、被活动流程引用的对象，不按文件年龄直接删除；任务管理和恢复仍运行。
- 任意账号已收藏即保护；收藏/取消收藏与清理需有共同并发保护。不要先查一次收藏，几秒后不复核就删除。
- 收藏音乐保护其歌词等依赖，即使依赖本身未显式收藏；父任务下有保护子项时不得级联删除父任务或整个音频目录。
- 先以数据库受控事务/可恢复删除状态确定范围，再处理文件与记录；设计文件删除失败、进程中断、重复运行的幂等恢复，不能删完文件再发现事务回滚留下“有记录无音频”。
- 只处理经验证位于配置存储根目录内的本地对象；S3按对象键删除。不跟随未知路径或把未知文件当垃圾。
- 提供管理员清理结果、失败原因和容量概况；不隐藏删除行为。已确认移除收藏后重新保留72小时，需新增可靠取消时间记录。
- 不自动清理记忆；日志/备份独立保留规则。不得以新三天策略覆盖原暂停流程48小时策略而不说明。

## 9. 迁移步骤与回滚

1. **预检**：读取仓库指引、本文与相关维护文档；核验服务器、Todo现状、端口、磁盘、架构、访问方式和待确认事项，输出实施清单。
2. **完整备份**：协调源机进入可访问状态，暂停新写入、确认在途生成/回调任务，安全导出PostgreSQL及音频与必要加密配置。记录时间、行数、文件数、字节数、校验和。`D:\DevTools\Backups\BlueMusic\20261018-consolidation\database.dump`只是旧备份且不含音频，不能代替本次最新备份。
3. **隔离恢复**：在独立临时数据库/卷恢复全量，验证记忆/收藏后，构造裁剪后的迁移数据集；只在副本裁剪，保留原始全量备份。本地原库不执行删记录。
4. **编写迁移工具**：提供dry-run、保护集合/依赖报告、事务边界、ID映射（如需要）和可重复执行策略。剪裁与传输都不启动worker，不把旧pending任务带入执行队列。
5. **服务器部署**：使用独立生产配置，按`alembic upgrade head`校验版本；不要对含真实数据的数据库随意`create_all`重建。导入后校准序列，避免新任务ID冲突；不迁移旧Redis队列、锁和在途消息。
6. **外网入口**：使用固定HTTPS入口并设置Suno回调根地址，保留签名校验；云服务器自身可公网访问时通常无需再穿透。旧任务已发出的回调地址不会因改配置自动更新，迁移前需处理/交接在途任务。
7. **受控启动**：先API只读核验，再按确认启动worker。真实收费生成和发通知先征得用户同意，不通过重放旧任务来验收。
8. **验收切换**：通过下表后才把新入口给用户；记录源库冻结时间，避免新旧两端同时写。回滚需处理切换后新增数据，不能简单覆盖回旧库。
9. **交付**：保存生产配置结构（脱敏）、备份恢复步骤、部署SHA、调度/自启动位置、磁盘告警方式与维护负责人，更新压缩记忆，commit/push代码；不得提交备份或密钥。
