# P4-P6 榜单、分析和作词维护说明

## 当前交付

```text
酷狗 TOP500 / 飙升榜实时采集
-> 按自然日保存快照
-> 默认读取连续 7 天排名变化
-> 输出 3 个结构化创作方向
-> 生成并保存标准段落歌词
-> 导出音乐平台通用创作方案
```

数据库默认保留最近 30 天榜单快照。同一天、同一榜单重复采集会替换当天条目，并把 `collected_at` 更新为最后一次成功采集时间；采集任务仍单独记录。TOP500 使用榜单代码 `8888`，飙升榜使用 `6666`；两类快照和上下文始终按榜单代码隔离。TOP500 用于连续日期趋势；飙升榜就是当前热度上升最快列表，不解释为几天数据，也不计算多日窗口。只有超级管理员可以触发采集、读取或删除采集运行记录；快照与歌曲详情对全部已登录成员只读开放。管理员榜单页展示最近 15 个快照结果和 15 次运行记录；成员榜单页只展示 TOP500、飙升榜各自最新一份及最后采集时间，每 15 秒同步并允许手工刷新。采集结果默认折叠，每个快照只显示日期、榜单、歌曲数和采集时间；点击某个快照后才请求并在结果块内展开该日排行榜详情，一次只展开一个快照。飙升榜默认采集前 20 首，可从其中任意一首直接进入单曲分析。分析页单独读取保留期内最多 100 份快照，并按最后采集时间倒序供用户选择；分析请求显式携带 `snapshot_id`，未勾选歌曲时分析当前所选快照前 30 首，而不是全局最新快照。

## 任务记录主动删除

采集运行记录、分析记录和作词记录都支持勾选后批量删除，也支持每条记录单独删除。三类批量接口都接收 `task_ids`，一次最多 100 条并自动去重；批量请求包含不存在或仍在运行的任务时整批拒绝，不会只删一部分。

- 删除采集运行记录只删除 `collection_tasks`，不删除 `ranking_snapshots` 和歌曲条目；自动流程保留快照编号。
- 删除分析记录会删除任务、报告和分析收藏；引用该报告的既有歌词继续保留，但解除来源报告和方向编号。
- 删除作词记录会删除任务、全部歌词版本和歌词收藏。
- 分析和作词的 `api_usage_records` 继续保留，用于 Token、费用和故障审计。
- 自动流程里的失效任务和产出编号会清空；采集步骤仍有快照时显示“运行记录已删除，快照保留”，分析或作词产出删除后显示“产出已删除”。

## 团队收藏夹

`favorite_items` 保存团队共享的收藏关系，不复制分析正文或歌词正文：

- `analysis + target_id` 指向一份具体分析报告。
- `lyrics + target_id` 指向一个具体歌词版本。
- 同一目标只有一条团队收藏，重复创建返回已有记录。
- 备注最多 2000 字，空白备注会标准化为 `null`。
- 原始产物生成时间与收藏时间分别展示；移出收藏夹只删除收藏关系。
- 来源账号删除后 `created_by_id` 自动置空，收藏和原始产物继续保留。
- 收藏来源不受最近 15 条历史列表限制，页面会按任务编号请求详情；后续自动数据清理必须跳过仍被收藏的报告和歌词版本。用户主动确认删除分析或作词任务时，对应收藏会同步删除。

收藏页一次读取最多 100 个精选条目，按收藏时间倒序并按类别筛选，页面每页展示 8 条。当前属于低并发内部团队功能；条目量显著增长后再改为服务端分页。

收藏关系还保存 `category`：`unclassified`、`S`、`A`、`B`、`C`、`D`。这些是
团队人工精选等级，和目标类型（分析、歌词、音乐）是两条独立维度；收藏页先按
等级切换，再按产物类型进一步过滤。音乐结果被收藏时仍只保存其结果编号，音频
和元数据继续由音乐模块负责。

## 固定歌词生成契约

客户确认后的正式作词规则统一定义在 `app.adapters.text_generation`，手工作词、重新生成、
自动流程作词和歌词 AI 修改共用同一契约：

```text
Verse 1 -> Verse 2 -> Chorus1 -> Chorus2 -> Interlude
-> Verse 2 -> Chorus1 -> Chorus2 -> Chorus1 -> Chorus2 -> Outro
```

- `theme` 表示歌曲类型或主题方向，例如励志、爱情、兄弟；`title_hint` 非空时必须使用
  该歌名，空值时允许模型先拟定歌名，再围绕歌名与主题完成表达。
- `Interlude` 和 `Outro` 的 `content` 强制归一为空字符串；最终正文只显示段落标记，
  不写歌词、纯音乐说明或占位文字。
- 同名重复段落使用第一次出现的完整歌词，防止重复副歌在一次生成中发生漂移。
- `Chorus1` 和 `Chorus2` 第一句由后处理统一为完全相同的一句，以稳定满足“相同或
  相似且有记忆点”的客户要求。
- 全部演唱句统一韵脚由 AI 提示词负责，要求模型返回前自行检查。当前不按句末单字
  机械判定押韵，因为中文同韵可以使用不同汉字，字符判断会误杀正常结果。
- Provider 返回值继续经过 Pydantic 校验；段落数量或顺序不符合契约、演唱段为空时，
  任务以 `LYRICS_PROVIDER_FAILED` 真实失败，不保存不完整歌词。

## 两种手工作词入口

歌词页由 `components/LyricsComposer.tsx` 展示两个模式，不再展示歌名、主题、标签、速度、
人声等旧参数表单：

- 根据分析创作：选择分析方向，另有可留空的细节调整输入框。服务端按报告编号和方向
  下标读取完整方向，包含配器、副歌建议和避免内容，不依赖前端拼装或提交这些参数。
- 自由描述创作：只输入一段创作要求，最长 2000 字。无需分析报告，AI 理解主题、歌名、
  曲风等；未指定的内容由模型合理补全。明确指定的歌名仍要求模型原样使用。
- 切换模式保留各自草稿，但自由描述请求不能带分析编号；失败不清空输入，生成期间
  禁止切换模式或重复提交。两个模式均沿用固定歌词契约、闲聊初筛和团队记忆。

新页面调用 `POST /lyrics/compose`，沿用 `LyricsUser` 权限。请求是以下两类之一：

```json
{"mode":"analysis","analysis_report_id":20,"direction_index":0,"prompt":"副歌更口语化"}
{"mode":"prompt","prompt":"写一首兄弟情的流行歌曲，歌名《并肩》"}
```

`services/lyrics.compose_lyrics` 将请求转入原有任务生命周期；旧 `/lyrics/tasks` 和
自动流程调用保留兼容，不要求修改其它 Agent。`lyrics_tasks.creation_input` 保存原始
模式、用户要求和分析方向快照，重新生成时继续使用该快照，不依赖随后变更或被删除的
分析报告。分析快照还用于音乐创作方案中的配器、副歌建议和避免内容。

`GeneratedComposedLyrics` 继承原有 `GeneratedLyrics`，同一次 Provider 响应还需返回
`creation_features`（主题、语言、曲风、情绪、场景、关键词、速度、人声性别与表达）。
任务保存实际采用的特点，供下游创作使用；不增加单独的“理解要求”AI 请求。字段不完整
时真实失败并保留用量记录，不保存半成品版本。`local` 后备仅作确定性演示，不代表真实
模型的语义理解或作词质量。

提炼内容只从本次有效用户输入和生成过程提取，不把闲聊或原始歌词写入长期记忆。
生成阶段仅把结构化 `memory_insight` 放在歌词版本上；用户保存作品或确认修改预览后，
才合并进团队记忆。只选分析也遵循同一确认边界，调试阶段不回填旧作品。

部署前先执行 `python -m alembic upgrade head`。作词入口迁移 `c9b5d7e2a410` 新增可空
`creation_input`；团队记忆迁移 `b6e4c8a2d710` 在其后新增单例记忆表和版本写入标记，
均不回填或修改旧作品。

## 歌词 AI 助手与版本确认

分析创作模式的“引用分析方向”打开当前页抽屉，按 `待分类 / S / A / B / C / D`
展示分析方向。未收藏或未分级的报告属于待分类，收藏报告按收藏等级展示；旧收藏不受
最近分析列表限制。界面显示 `AnalysisTask.id`，避免把内部 `AnalysisReport.id` 当作
用户看到的任务号。确认方向后服务端自动传参，用户可通过细节输入框调整；生成完成后
仍可打开原有 AI 助手继续提出修改要求。

```text
当前歌词版本
-> POST /lyrics/versions/{id}/assistant
-> 记录用户要求和 AI 预览
-> 用户继续对话，或确认预览
-> POST /lyrics/assistant-previews/{message_id}/confirm
-> 新建正式 LyricsVersion
```

预览消息保存在 `lyrics_assistant_messages`，用于恢复本次对话；它不是正式歌词
版本，也不会改变当前版本内容。只有确认接口才会创建新的 `LyricsVersion`，因此
收藏、引用和历史版本均稳定可追溯。

所有会影响歌词创作的自由文本先经过 `app.services.lyrics_prompt` 本地初筛。手工作词的
主题和补充要求、歌词/审核 AI 助手的修改要求、自动流程作词配置及一键参考创作要求均
使用同一规则。明确的寒暄、测试语和无关闲聊会在创建任务、对话消息或记忆证据之前返回
`422 / LYRICS_PROMPT_IRRELEVANT`，前端用警告提示用户直接填写主题、风格、情绪或具体
修改要求。初筛只拦截确定性较高的闲聊，不额外调用 Kimi，避免每次提交翻倍消耗、延迟
和限流风险；包含明确创作意图的正常表达继续进入原有 Provider。

## 歌词创作提炼 Skill 与隐藏记忆

`app.services.lyrics_memory` 只维护一份全账号共享的 `lyrics_team_memory`。旧的事件和快照表
保留在数据库中以免破坏历史数据，但运行时不再读取，也不再提供逐条证据、启停、删除、
快照或注入预览管理。普通成员不能读取隐藏记忆；超级管理员在“歌词创作”页点击“团队记忆”
打开抽屉，查看完整合并结果、确认作品数、记忆版本和单次注入数量。

首次生成和 AI 修改仍在原有 Provider 响应中同时返回 `memory_insight`，结构为用户偏好、
创作方法、有效结果、复用规律和亮点经验。生成成功或修改预览成功只把提炼结果保存到
`lyrics_versions.memory_insight`，不会立刻污染长期记忆。只有以下两个显式确认动作才写入：

```text
PUT  /lyrics/versions/{version_id}/save
POST /lyrics/assistant-previews/{message_id}/confirm
```

写入时采用本地确定性合并，不额外调用 Kimi。系统只在同一类别内比较归一化文本、包含
关系、字符相似度和相邻字符集合；命中相似项时保留信息更完整的表述、累加
`evidence_count` 并移到队首，没有命中时新增。`lyrics_versions.memory_committed_at` 保证
同一版本重复点击保存不会重复学习。原始提示词、闲聊、歌词正文和未确认草稿均不写入
团队记忆；调试阶段不回填旧作品。

`build_lyrics_skill_context` 只读取这一份团队记忆，并按当前顺序截取管理员设置的前 N 条。
默认 N 为 60，超级管理员可在同一个抽屉中设置 1 至 200；此值只影响每次发送给文本 AI 的
上下文数量，不删除库内内容。团队记忆最多保留 300 条合并结果，当前任务明确要求始终高于
历史经验，历史内容仍按不可信数据处理，不得覆盖系统契约或原创性规则。

管理员通过同一抽屉中的 AI 对话直接修改整份记忆。`POST /lyrics-memory/chat` 把管理员要求、
当前完整记忆和最近对话发给活动文本 Provider，Provider 返回修改后的完整结构；后端校验、
去重后立即保存，并把调用写入 `api_usage_records`。修改失败时事务回滚，原记忆保持不变。
注入数量使用独立的 `PATCH /lyrics-memory/settings`，不会交给模型猜测。

迁移 `b6e4c8a2d710` 新增 `lyrics_team_memory` 和
`lyrics_versions.memory_committed_at`，前序为 `c9b5d7e2a410`。部署或恢复开发环境后必须先
执行 `python -m alembic upgrade head`。

## 文本 AI 配置

系统按以下优先级选择文本模型：

1. 读取数据库中唯一的活动 `ai_provider_configs` 配置。
2. 没有数据库活动配置时，使用 `.env` 中的 `AI_*` 后备配置。
3. 后备配置为 `local` 时使用免费、可复现的本地规则基线。

超级管理员在“AI 接口”页面新增、测试并启用配置。切换会在下一次分析或作词调用开始时立即生效，不需要重启后端；已经开始的任务持有启动时解析出的 Provider，不会在执行中途换接口。

系统预置本地规则、智谱 BigModel、Kimi 开放平台、DeepSeek、阿里百炼 Qwen、MiniMax 和通用 OpenAI-compatible 模板。模板提供官方 Base URL、默认模型和协议差异，实际模型名仍可编辑。

仓库后备配置：

```env
AI_PROVIDER=local
```

`local` 用于未配置环境、自动化测试和外部平台故障降级，不应对客户宣传为正式大模型效果。

当前本机活动配置为 Kimi 中国区官方接口 `kimi-k3`，用于付费开发稳定性测试；智谱 `glm-4.7-flash` 和本地规则继续作为已保存的后备配置。Kimi API Key 使用 Fernet 认证加密保存，API 和页面只返回末尾提示。该测试密钥不进入生产环境，上线前必须切换正式密钥并在 Kimi 控制台吊销测试密钥。

选定正式文本模型后配置：

```env
AI_PROVIDER=openai_compatible
AI_BASE_URL=https://供应商的兼容接口/v1
AI_API_KEY=只保存在服务器环境变量中
AI_MODEL=供应商模型名
AI_CONFIG_ENCRYPTION_KEY=长期稳定且只存在于服务器的加密主密钥
AI_REQUEST_TIMEOUT_SECONDS=180
AI_MAX_RETRIES=2
AI_ANALYSIS_MAX_OUTPUT_TOKENS=2500
AI_LYRICS_MAX_OUTPUT_TOKENS=3500
```

正式模型返回值仍要经过 Pydantic 结构校验。缺字段、错误类型、超时或无效 JSON 都会令任务失败并保存错误码。
智谱 GLM-4.7/5 系列默认会思考；当前结构化分析和作词不需要深度推理，适配器仅对该系列发送 `thinking.type=disabled`，并使用上述输出上限控制时延和用量。其他 OpenAI-compatible 供应商不会收到这个智谱专用参数。

Kimi K3 使用 `max_completion_tokens`，固定采样参数且始终开启思考。适配器不会发送不受支持的 `temperature`，使用官方 `reasoning_effort=low` 控制开发阶段时延和费用，并保留 `response_format=json_object` 结构化输出。连接测试上限为 256 Token，分析和作词仍使用各自配置的输出上限。

`AI_CONFIG_ENCRYPTION_KEY` 未配置时暂时回退到 `SECRET_KEY`。生产部署应显式设置独立值并长期保留；修改或丢失该值会导致已经保存的 API Key 无法解密，需要重新录入。活动配置禁止直接编辑和删除，必须先切换到其他已测试配置。

## API 用量记录

分析和作词每次执行都会新增一条 `api_usage_records` 记录：

- 记录任务类型和任务编号、供应商、模型、请求方法、接口地址及供应商请求编号。
- 智谱等 OpenAI-compatible 响应中的 `usage.prompt_tokens`、`usage.completion_tokens`、缓存 Token 和总 Token 会按原值保存。
- 本地规则执行也会留下记录，但明确标记为非外部调用且 Token 为 0。
- 失败调用保存接口、重试次数、耗时和错误信息；供应商未返回用量时保持 0，不做字符数估算。
- 旧任务不会补造 Token，因此页面会显示“历史任务未记录接口”。
- Dashboard 按应用时区统计今日和近 7 日用量。Kimi 活动配置通过官方 `/v1/users/me/balance` 显示人民币可用余额；查询仅向超级管理员开放，失败时不阻断业务任务。智谱余额仍由超级管理员通过供应商控制台查看。

## 分析边界

- 只使用榜单元数据和排名变化，不下载酷狗音频。
- 曲风、情绪、乐器和人声是创作建议，不是对原曲的事实检测。
- 不输出准确 BPM、调性、和弦或要求复刻具体歌曲、歌手。
- 有效数据不足 7 天时仍可分析，但报告会显示较低或中等可信度。
- 酷狗公开榜单未提供的热度和封面保持为空，不制造假数据。

## 云端注意事项

- `APP_TIMEZONE=Asia/Shanghai` 统一快照日期和 Dashboard 的“今日”边界。
- 生产环境执行 `alembic upgrade head` 后再启动新版后端。
- `favorite_items` 使用 Alembic 迁移创建，云端升级前必须先备份 PostgreSQL，再执行迁移。
- `api_usage_records` 从功能上线后开始记录，数据库迁移不会伪造旧任务用量。
- 当前是低并发内部工具，采集、分析和作词在 HTTP 请求内完成；隐藏作词记忆与正式创作合并为一次模型调用，不额外消耗一次接口请求。若正式模型响应经常超过一分钟，再将任务执行迁移到 Redis 队列，不提前增加维护成本。
- Docker 和云端部署必须给所有后端实例提供相同且稳定的 `AI_CONFIG_ENCRYPTION_KEY`；滚动部署不影响数据库活动配置和热切换。
- 酷狗页面结构变化时先运行解析器测试，再根据 `CRAWLER_SOURCE_UNAVAILABLE` 任务编号检索日志。
