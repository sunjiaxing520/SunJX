### 4. “Hadoop 集群怎么扩容？”

**思路：先分清存储还是计算 → 新节点对齐环境 → 注册检查 → 限速均衡和验收。**

> 我会先确认缺的是存储空间还是计算资源，不能只说加几台机器。存储扩容主要增加数据节点，计算扩容主要增加运行任务的节点；一台机器是否同时承担两种角色，要看原来的架构。准备阶段会核对软件版本、主机名、时间同步、网络、磁盘挂载和权限，也要补齐认证及机架信息。按团队流程配置新节点，必要时更新准入名单，让服务注册到集群后，先检查节点健康、可用容量和资源识别是否正常。旧数据不会因为加机器就立即平均分布，需要在低峰期按带宽限制做数据均衡。最后验证读写和代表性任务，观察副本、磁盘及网络指标，并更新监控和容量记录。整个过程分批推进，异常时先停止继续扩容。

⭐ 补充理解：DataNode 管 HDFS 存储，NodeManager 管 YARN 节点资源；添加机器通常不需要停整个集群。HDFS Balancer 用于节点间数据均衡，DiskBalancer 处理单节点的磁盘分布，两者别混。扩容及均衡依据：[HDFS 用户指南](https://hadoop.apache.org/docs/r3.3.6/hadoop-project-dist/hadoop-hdfs/HdfsUserGuide.html#Balancer)。

### 5. “NameNode 挂了怎么办？”

**思路：确认影响和故障位置 → 看有无 HA → 保护元数据 → 验证恢复。**

> 我会先确认是进程故障、机器故障，还是网络不通，并查看业务影响、告警和日志。如果集群已经配置高可用，就检查备用节点是否健康、共享编辑日志是否正常，以及故障转移是否成功。自动切换依靠故障转移控制器监测状态，再通过协调服务选出主节点；切换过程中还要隔离旧主，避免两个主节点同时工作。如果自动切换失败，我会先上报并按既定预案处理，不直接强制抢主。如果没有高可用，就要保护现有元数据，在确认原因后恢复原服务，必要时按备份和编辑日志进行恢复，不能格式化。辅助名称节点主要做检查点，不是能直接接管的热备。恢复后还要验证读写、任务及副本状态，再复盘原因。

⭐ 对应术语：高可用是 **HA**；故障转移控制器是 **ZKFC**；协调服务是 **ZooKeeper**；共享编辑日志通常由 **JournalNode** 保存；隔离旧主叫 **fencing**。非 HA 的恢复程度取决于保留下来的元数据，不能保证一定零丢失。依据：[HDFS HA 官方说明](https://hadoop.apache.org/docs/r3.3.6/hadoop-project-dist/hadoop-hdfs/HDFSHighAvailabilityWithQJM.html)、[Secondary NameNode 职责](https://hadoop.apache.org/docs/r3.3.6/hadoop-project-dist/hadoop-hdfs/HdfsUserGuide.html#Secondary_NameNode)。

### 6. “Spark 任务跑得慢怎么排查？”

**思路：先分等待和运行 → 找最慢阶段 → 用指标判断瓶颈 → 一次验证一种改动。**

> 我会先分清任务是在排队，还是已经运行但执行慢。如果一直处于已接收状态，就先看资源管理页面里的队列容量、可用资源和应用启动资源限制，这时调整计算逻辑未必有用。如果已经运行，就看任务页面，找耗时最长的阶段，比较各个任务的数据量、耗时和失败重试情况。少数任务特别慢，要怀疑数据倾斜；整体都慢，再看读取量、网络传输、磁盘落盘、内存回收和资源分配。确认原因后再选择分区裁剪、提前过滤、预聚合、合理调整并行度，或者针对热点键拆分处理。资源参数也要结合队列余量来调，不能一味加内存。改完用同一批输入比较耗时和资源消耗，同时确认结果一致。

⭐ 追问“数据倾斜”：同一批任务里，少数任务分到的数据特别多，其他任务结束了它还在跑。加盐需要配套聚合还原或正确的连接逻辑，不能给键随便加随机数就算完成。依据：[Spark 监控指标](https://spark.apache.org/docs/3.5.6/monitoring.html)、[Spark SQL 性能优化](https://spark.apache.org/docs/3.5.6/sql-performance-tuning.html)、[Spark on YARN](https://spark.apache.org/docs/3.5.6/running-on-yarn.html)。

### 7. “Hive 小文件问题怎么解决？”

**思路：说明两类成本 → 找来源 → 按格式和引擎合并 → 从写入端预防。**

> 小文件的问题不只是占磁盘。文件和数据块的信息要由名称节点管理，数量太多会增加内存压力；查询时还会增加文件打开、扫描和任务调度的成本。我会先看文件数量、平均大小和产生方式，确认是写入太频繁、分区太细，还是输出并行度不合适。处理时要看表格式和执行引擎，支持合并的格式可以采用对应的合并方式；其他情况可以在临时表或新路径重写数据，核对结果后再按流程切换。事务表要使用适合它的压缩合并机制，不能直接拼文件。长期会调整写入批次、分区粒度和输出文件数量，并观察查询速度及资源变化。也不会为了消除小文件，把所有数据都挤成一个超大文件。

⭐ `CONCATENATE` 是 Hive 的一种合并能力，主要针对符合条件的 RCFile、ORC；不能笼统宣称所有格式、所有事务表都能这样合并。读入时合并扫描任务也不等于 HDFS 上的小文件已经消失。依据：[Hive DDL 中的合并说明](https://hive.apache.org/docs/latest/language/languagemanual-ddl/#alter-tablepartition-concatenate)、[Hive ORC 说明](https://hive.apache.org/docs/latest/language/languagemanual-orc/)。

## 四、⭐ 反问环节：优先选两到三个

反问的目的，是弄清入职后的真实工作和要求。先问业务与团队，再视时间询问技术方向；不必连问四题。

| 想了解什么 | 可以直接问 | 为什么这样问／如何接话 |
|---|---|---|
| 集群规模和压力 | “想了解一下，目前主要维护的集群大概是什么规模，日增数据量在什么量级？日常最关注哪类稳定性问题？” | 了解节点、容量和故障重点；不用追问具体客户或敏感配置。可以接“这样我也能更有针对性地补基础”。 |
| 运维与开发比例 | “这个岗位日常运维和开发大概各占多少？开发主要是巡检脚本、数据处理，还是平台功能？” | 判断 Python 能力如何使用，以及岗位实际工作是否匹配。 |
| 大模型应用阶段 | “如果团队有大模型相关工作，目前是在探索验证、立项建设，还是已有应用运行？运维岗位主要参与哪个环节？” | 先保留“如果”，避免假设公司一定在做；把兴趣落到职责上。 |
| 团队分工与上手要求 | “目前团队大概几个人，运维、开发和数据治理怎么分工？对新同事前三个月有什么具体要求？” | 了解协作、支持和成长预期；可接着确认值班交接安排。 |

## 五、⭐ 临场卡壳时的三句话

- 没做过：“这类生产场景我还没有直接处理过，我可以先说一下排查思路，再说明哪些地方需要查文档确认。”
- 不确定版本：“这个细节会受组件版本和部署方式影响，我会先确认版本和现有配置，不直接套一个固定答案。”
- 被连续追问：“我先确认一下，现在的问题是任务还没启动，还是已经运行后变慢？这两种情况排查入口不一样。”

**🔥 最后只记五个动作：确认影响 → 收集证据 → 定位原因 → 按流程处理 → 验证并复盘。**

4. [Apache Spark：在 YARN 上运行](https://spark.apache.org/docs/3.5.6/running-on-yarn.html)——YARN 资源申请、部署模式及容器资源。

6. [Apache Hive：DDL 手册](https://hive.apache.org/docs/latest/language/languagemanual-ddl/)及 [ORC 手册](https://hive.apache.org/docs/latest/language/languagemanual-orc/)——小文件合并的格式限制及具体语义。
